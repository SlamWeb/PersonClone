# PersonClone Persona Wiki V2：批量编译与观点冲突

日期：2026-09-25。**这是下一版设计决策，不表示以下构建器已实现。**当前运行资产仍是 `persona_wiki.json`：它把已核验的 Persona Pack claim 与 Narrative Schema facet 确定性合并成 `core + cards`，`shared_source_links` 只表示共用原文。当前 Web 会把整份资产放进固定前缀，原文检索仍独立运行。本设计保留这个运行原则，但重做 Wiki 的构建与维护。2026-09-25 的后续讨论明确：不给 Writer 提供 Wiki 搜索时，**运行时不传目录、路径、索引、doc_id 或原文摘录清单**。

![Persona Wiki V2 建库侧结构示意；图中的 doc_id 仅用于离线追溯，不进入 Writer 提示词](persona-wiki-v2-map-interview.png)

## 决策

每位作者维护一个持久的 Persona Wiki：**作者总纲 + 按议题组织的主题页 + 一份作者级风格页 + 少量有证据的跨主题关系**。原文 `parents.jsonl` 仍是事实来源。建库资产保留原文指针；Writer 只看可读的世界观、条件、变化、风格和真正有价值的关系。本轮具体事实仍由现有 Raw RAG 提供。V2 不做 Wiki 的查询时检索、循环读页或 Agentic Search。

Wiki 是“一次编译、重复使用、可追溯地持续修订”的作者知识资产。这里的“页”是一个**语义单元**，第一版不必做成一棵 Markdown 文件树：数据上可以是一份版本化 JSON 中的多条主题记录，展示时再按页渲染。页面和关系在**离线构建**时使用；即使当前没有查询时遍历，它们也能防止不同文章对同一问题的条件、变化和来源被压扁。论文中 LLM-Wiki 的多跳收益不能直接外推到本项目的“整份 Wiki 入上下文”模式，必须另做作者语料评测。

## 两种视图：建库资产与 Writer 文本

```text
author/
  persona_wiki_v2.json       # 总纲、topics[]、style、少量有类型的关系；按版本发布
  persona_wiki_sources.jsonl # 每条候选观察和观点的 doc_id、原文摘录、时间、哈希
  persona_wiki_build.json    # 已处理文档哈希、pending 批次、构建版本与校验结果
  index/parents.jsonl        # 作者原文，独立保存；事实来源
```

不为 Writer 建 `index.md`、文件路径或检索工具。内部的 `topic_id`、`claim_id`、来源账本是**维护和追溯所需的键**，不等于面向回答模型的搜索索引。可读 Markdown 页面仅在需要人工浏览或导出时由同一份 JSON 生成，不维护第二份可能漂移的知识。关系保存在观点之间，不需要图数据库。

每条观点内部至少记录：`claim_id`、`topic_id`、审慎转述、作者/被引用者归属、语境类型（本人主张/引用/假设/反讽/不确定）、适用条件、边界、`doc_id + excerpt + source_hash`、发表时间和状态。时间缺失保持未知，不从导入时间伪造。旧 Pack/Schema 的条目只作为有来源的**候选观察**迁入，不能仅凭标题相似自动合并。

**Writer 文本**只确定性渲染总纲、所有主题页的有价值内容、作者级风格页及必要的时间/条件/跨主题关系；不传内部 ID、哈希、路径、来源目录、完整摘录或构建日志。它需要具体细节时，依旧由本轮 Raw RAG 补原文。“整份 Wiki 入上下文”指完整的已发布**知识视图**，不等于作者所有原文全文。

“有价值”优先指反复出现或作者明确自述的判断原则、与其他作者可区分的观点、适用条件/反例、真正的观点转变、跨主题共同原则和可验证的表达习惯。一次性文章细节、他人观点、同义重复和缺少来源的性格形容词不挤占固定前缀。出现次数不是唯一标准：一次明确且重要的自我表述可以保留，但应标明证据范围，不伪装成跨文章共识。

## 主题页长什么样

一个主题页回答一个稳定的问题域，例如“作者如何看待亲密关系”“如何选择工作”“怎样理解人生中的风险”。**爱情观、人生观、工作态度可以是初始大类，但不作为封闭枚举**；不同作者可能形成完全不同的主题。尤其“人生观”容易过宽：它适合作为综合页，下面的“自由与责任”“失败与风险”等可在证据足够时成为独立主题。

每页有以下内容，字段可以为空，但不能编造：

| 内容 | 具体记录 | 给 Writer 看什么 |
| --- | --- | --- |
| 主题边界 | 本页回答的问题、包含/不包含的情境 | 一句清楚的议题范围 |
| 当前综合 | 几篇材料共同支持的倾向；证据不足则不写成稳定立场 | 自然语言概括，而非抽象标签 |
| 观点组 | 多个具体主张；每条附对象、前提、条件、例外和反例 | 有条件的判断，不是绝对化口号 |
| 时间与变化 | 观点何时出现、后文是否明确修正；互斥但未确认的观点并存 | 简短说明演变或不确定性 |
| 跨主题关系 | 哪个具体观点支持、限定或挑战另一主题的观点 | 只渲染能帮助理解的关系句 |
| 来源账本 | 每个观点的 doc_id、短摘录、时间、哈希 | **不进入固定前缀**；供校验与审计 |

例如一篇文章同时谈婚姻、职业与个人自由，应抽取多个观察，分别归入“亲密关系”“工作态度”“自由与责任”；原文不是只能属于一个聚类。若作者明确说“我选择工作的原则与亲密关系一样，都是尊重彼此的自主性”，才创建有证据的跨页“共同原则”关系。单纯同时提到两个主题或 embedding 相近，不足以建边。

**纯虚构示例，用于说明页内粒度，不代表仓库中的任何作者：**“工作态度”页可分为“选择职业时看重什么”“怎样看待稳定收入”“如何与团队协作”三个子问题。若甲在一篇材料说“生计稳定时优先长期成长”，另一篇说“家庭支出很重时要先保证现金流”，Wiki 应写成“一般重视长期成长，收入压力大时优先稳定现金流”，并在建库资产中分别保存两处证据；这不是让模型任选一个绝对立场。Writer 只收到这句有条件的综合，不收到文章路径和内部 ID。

**何时新开主题页：**候选内容提出一个与已有页面不同、以后可以独立被问到的判断问题；塞入旧页会模糊旧页的范围或条件；且有可追溯的作者原文。来自单篇文章的清晰而重要的立场可先建“暂定主题”，但不能直接上升为作者的稳定总纲；零碎提及先作为已有页的子观点。已有页积累了几组各自可独立提问的观点时再拆页。主题名称、拆分和合并由批次编译决定，并以稳定 `topic_id` 追踪，不靠硬编码的爱情/人生/工作分类。

**何时连接两页：**只在能够写出“观点 A 如何支持、限定、形成张力或修正观点 B”的一句具体说明且能指回原文时建立关系。关系先落在观点级，再派生为页级概览；普通话题相似不建关系。真正的前后改口使用 `supersedes`，条件不同使用 `qualifies`，尚不确定的矛盾使用 `tensions`，都保留两端证据。

## 风格页长什么样

风格页是**一位作者的一份表达画像**，而不是“幽默、温柔、理性”这类形容词堆。记录可观察的用词/语气、句式与节奏、论证顺序、如何进入问题、举例或反问方式，以及这些模式适用的情境和明显例外。每项都由多段原文示例支持；单篇的特殊文体不写成永久风格。避免存“每次都要用 X 开头”之类固定模板，保留作者表达的变化。给 Writer 的文本是短的可操作描述，例如“常先界定问题范围，再给判断和例外”，而不是原文例句清单；原文示例仍在来源账本，具体模仿材料由本轮 Raw 上下文提供。风格观察允许彼此并存：作者可能在讨论技术时给出密集推理，在私人话题中使用短句；有证据才写“依情境变化”，不强制拆成聊天版和问答版。

## 初建与低成本批量更新

### 论文做法与本项目取舍

[Karpathy 的原始构想](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)强调 raw/wiki/维护规则三层：新增来源后更新相关的主题/实体页、目录和日志；他个人偏向逐篇检查，但明确允许批量 ingest。这是设计模式，不是一个确定的抽取算法。[微信团队 LLM-Wiki 的 Algorithm 1](https://arxiv.org/html/2605.25480v2)则以 **source batch 为输入，逐 passage 选相关现有页、编译页面/链接、做结构与内容校验、记录错误并局部修复**。其 `index.md`、别名和路径主要服务于查询时 `wiki_search`/`wiki_read`。我们不做这些查询工具，因此只借鉴“来源批次、局部合并、证据校验、版本化发布”，不复制文件树和搜索目录。

对 PersonClone，**先按整篇文章做互斥聚类，再把整个簇扔给 LLM 并不合适**：一篇文章可能同时谈爱情、工作和人生；标题聚类也抓不到正文中的次要但重要的观点。合理顺序是“分批读来源 → 抽取带证据的原子观察 → 对观察做软聚类/多主题归属 → 按主题合并”。现有 `narrative_builder.py` 的 BGE-M3 标题聚类可作候选主题提示和分批取样工具，但它只选代表文章，不能替代对全部合格原文的覆盖。

### 初建：覆盖全部合格原文

1. 固定一次原文快照，按 `doc_id + 正文哈希` 去重，保存标题、来源类型和真实发表时间；记录每篇是否已处理。长文按语义段切开，但每段携带同一篇文章的标题与语境，避免断章取义。
2. 按**输入 token 预算**把多篇短文或少量长文段组成抽取批次，用便宜模型一次输出分文档的结构化观察：作者本人主张、其对象/条件/例外、是否引用他人、短原文摘录、可能的时间变化，以及风格信号。无有价值观察允许空结果。不要直接让模型在这个步骤写最终“世界观”。
3. 程序逐字核对每个摘录及 `doc_id`；被引用者的话不能被提升为作者立场。记录为可重试的来源账本，而非无证据的自由格式 Source Digest。摘要可作为人工审计的派生视图，但 V2 不强制增加一层可能失真的压缩。
4. 对**观点观察**做 embedding + 关键词辅助的软聚类，一条观察可以归多个候选主题；风格观察另归并。模型只看某主题的候选观察与邻近旧页，合并相同主张、保留条件/反例/冲突，决定建页、补页或拆页。再依据确有证据的观点关系生成少量跨主题连接。
5. 从已合并主题页生成作者总纲；从跨来源风格观察生成风格页。总纲不把单篇观点写成稳定人格。对全部来源做 coverage 检查，报告“有观点、只有风格、无可提炼内容、抽取失败”的数量，不能让未处理文章静默消失。

抽取批次的篇数由输入 token 和输出长度决定，不以“一篇一调用”或“一个聚类一调用”作为硬规则。初建费用要记录调用次数、输入输出 token、耗时、作者覆盖率和校验失败率，再决定合适的批量大小。

### 增量：先积累，再合并受影响主题

**新增文章先入 pending 清单**，对话继续使用最近一次已发布 Wiki；新内容可由 Raw RAG 按现有索引路径回答。离线触发采用可配置的“积累到一定篇数/原文 token、达到最长等待时间、或手动运行”三选一，例如初始实验值为 10 篇、3 万原文 token 或 7 天，实际阈值用真实作者增量分布调参。每篇用 `doc_id + 正文哈希` 判定新增、修改和删除；不能只用 `updated_at`，因为当前 `compute_corpus_version` 仅哈希 `doc_id + updated_at`。**修改或删除不是普通待处理新增**：须先确定性地屏蔽受影响观点及证据，或阻止旧 Wiki 继续被服务使用，然后再批量语义重编；不能让已失效引用等到下一周仍被当作现行依据。

对 pending 文档复用初建的抽取和观点聚类。路由时只把**现有主题标题与简短范围说明**给编译模型，不需要查询时搜索索引；同一批的候选先聚合，再对每个受影响主题**合并一次**。仅当受影响观点改变总纲或风格时才刷新它们；未变主题及 ID 保持不变。修改/删除源文时撤销无效证据并重判其依赖观点。

发布前程序验证作者归属、逐字摘录、来源哈希、唯一 ID、关系两端、字段完整性和 50k Wiki 文本预算；模型仅检查受影响主题与相邻冲突，判断误归属、过度概括或漏记反例。固定的“条件区别、前后观点、出处、风格”探针题比较新旧版本。验证失败则保留旧 Wiki 和 pending；对删除/改写导致的失效引用仍维持屏蔽或停用。验证通过后原子切换版本。先用明确的错误记录和重试，暂不实现论文完整 Error Book。

Wiki 增量更新与 Qdrant 增量入库是两个任务。当前 `build_corpus` 会重写 parent/node 文件，`index_corpus(..., recreate=True)` 默认重建 collection；V2 Wiki 可以先按文档哈希增量编译，不能因此声称原文索引也已经增量化。改动或删除原文后，两者必须最终指向同一语料版本；上线前做一致性检查。

## 前后观点冲突

冲突不是简单“新覆盖旧”。先确认两句是否都在表达**作者自己的立场**；引用他人、反讽、设问、假设和事实报道不能直接算作者观点。再比较主题、对象、适用条件和时间：

| 情况 | Wiki 处理 | Writer 使用 |
| --- | --- | --- |
| 条件不同，例如不同对象或不同前提 | 两条都留；用 `qualifies`/条件字段说明边界 | 按当前问题条件选用，不说作者自相矛盾 |
| 作者明确说“以前认为 A，现在改为 B” | 保留 A、B 两条与各自来源；建立 `B supersedes A`，A 标历史观点 | 如问现在的立场，优先 B；如问变化，交代 A→B |
| 同一条件下互相抵触，但没有明确修正 | 两条都留，标 `tensions`/待判，不自动以较新者获胜 | 说明作者在不同文本有不一致表达；不合成确定立场 |
| 来源、归属或日期无法确认 | 保留证据和“不确定”状态，不进入确定性总纲 | 必要时查本轮 Raw；仍不足就保留不确定性 |

例如，作者 2023 年写“我倾向远程办公”，2025 年写“对于需要密集带教的新团队，我更支持线下”：先记录**适用条件变化**，不能直接生成“作者全面转向线下”。只有后文明确否定此前的一般主张，且来源/语境可靠，才标记 `supersedes`。低价模型可提出候选冲突，不应自动覆盖旧条目；程序能验证引文存在，但不能证明语义归属或立场变化正确。

## 50k Wiki 上限

`50,000 token` 是**已渲染 Wiki 自身的硬上限，不是目标长度或质量保证**。先消除重复，再缩短冗长表述并重跑探针；超过上限或质量退步的版本不发布，不在运行时静默截断。完整原文仍保留在 `parents.jsonl`。长上下文能装下并不等于模型一定读对，特别要测试跨页观点、条件和时间冲突。

按本轮确定的运行前提，Writer 采用长上下文模型；**当前 Web 默认的 64,000 配置不是 Wiki 构造的约束**。切换 V2 运行路径时相应调整项目配置即可。Wiki 的 50k 限额应以实际使用的 tokenizer 计算；现有 `estimate_tokens` 仅为粗估。

## 实施顺序与验收

1. 先建立 V2 数据契约、渲染器和校验器；把 V0 Pack/Schema 项迁成候选条目。用不含真实语料的 fixture 验证来源、时间、条件和冲突关系。旧 `mrprompt` 继续工作。
2. 做一次完整作者离线编译，输出主题页、总纲、风格页和诊断报告。先在一个作者上核对覆盖率、Wiki token、构建费用及冲突误判，再扩展到其他作者。
3. 加 pending 批次和受影响页面更新，验证新增、改写、删除与失败回滚；再接到作者导入流程。原文索引的增量化可独立推进。
4. 最后切换 Writer 到 V2 固定前缀，同时保留本轮 Raw RAG。以相同问题集比较 V0 与 V2 的作者观点一致性、单篇细节、前后变化、风格、成本和延迟。未达到质量门槛时回退 V0。

## 一手依据与适用边界

- [Karpathy 的 LLM Wiki 原始构想（idea file，2026）](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)：raw/wiki/schema 三层，支持批量 ingest 与周期 lint；不是已验证的产品实验。
- [LLM-Wiki，腾讯/微信团队，arXiv 预印本（2026）](https://arxiv.org/html/2605.25480v2)：结构化页、双向链接、source archive、按批选择/更新相关页及校验；其查询收益主要结合渐进式遍历，本设计仅借鉴**离线编译**部分。
- [WiCER，arXiv 预印本（2026）](https://arxiv.org/html/2605.07068)：压缩可能漏掉关键事实，长上下文也有注意力问题；因此用定向探针验证 V2，而不把 50k 当作效果保证。
- [PGMem，arXiv/EMNLP 2026](https://arxiv.org/html/2608.01708)：人格证据中的支持、矛盾、转变关系及自动判定误差；研究对象是用户对话记忆，迁移到作者文章属于工程推断。
